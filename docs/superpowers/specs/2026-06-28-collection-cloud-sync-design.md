# 项目进度合集云同步设计

## 目标

为项目进度页面增加匿名、免密码、跨设备的 Firebase 云同步。不同设备输入同一个“项目进度同步码”后，通过合集合并得到双方数据；任何一台设备都不能用整块本地数据盲目覆盖云端。

云同步控制区放在页面最底部，标题为“云同步与数据”，默认折叠。

## Firebase 隔离

- 复用现有 Firebase 项目 `daily-calorie-tracker-3ec47`。
- 每日卡路里继续使用 `syncSpaces/{syncCode}`。
- 项目进度使用独立集合 `projectCheckinSyncSpaces/{syncCode}`。
- 项目进度的同步码、deviceId 和连接状态使用独立 localStorage 键，不读取每日卡路里的同步码。
- Firestore 规则同时保留两个集合，更新规则不能破坏每日卡路里同步。

项目进度同步码由浏览器生成 20 位大写字母和数字，接受 12–24 位。知道同步码并通过匿名登录的设备可以访问对应文档，因此同步码必须保持私密。

## 状态分层

### 同步内容

以下内容参与云同步：

- 项目及其顺序。
- 每个项目每天的打卡。
- 三个随机分类的名称和自定义条目。
- 每日最终随机结果。
- 阶段项目及当前阶段。
- 页面标题、阶段看板标题、阶段名称和主题等设置。

### 设备本地界面状态

以下内容不参与云同步，以避免远端快照打断当前操作：

- 每日、每周、每月的当前选择。
- 当前查看日期或月份。
- 折叠区域的展开状态。
- 搜索框、对话框、输入草稿、悬停行列和滚动位置。

应用远端数据时保留这些本地状态，并保持现有组件 key 稳定，不重新挂载折叠区域。

## 同步元数据

每台设备首次运行时生成一个 UUID，永久保存为 `project-checkins:device-id`。导入文件不得覆盖本机 deviceId。

版本戳为：

```ts
type VersionStamp = {
  updatedAt: number
  updatedBy: string
}
```

`updatedAt` 使用单调客户端时间：

```ts
Math.max(Date.now(), latestObservedTimestamp + 1)
```

时间相同时以 `updatedBy` 字符串排序作为确定性决胜条件；仍相同时以规范化 JSON 排序，保证交换合并和重复合并结果稳定。

## 实体与唯一 ID

应用继续使用当前适合渲染的数组和对象形状，并增加 `syncMeta` 保存实体版本和 tombstone。

- 项目：沿用项目 `id`；增加稳定的 `order`。
- 打卡：逻辑 ID 为 `${projectId}:${dateKey}`。
- 随机条目：沿用条目 `id`；增加分类 ID 和稳定的 `order`。
- 每日随机结果：逻辑 ID 为 `${dateKey}:${categoryId}`。
- 阶段项目：沿用阶段项目 `id`。
- 设置：每个设置键独立版本化，例如 `title`、`theme`、`stageBoardTitle`、`stageLabel:0` 和 `categoryName:fitness`。

同名但 ID 不同的项目或条目必须分别保留。

## Tombstone

删除不立即忘记 ID，而是在 `syncMeta.tombstones` 中永久保留版本戳。

需要 tombstone 的类型：

- 项目。
- 打卡。
- 随机条目。
- 每日随机结果。
- 阶段项目。

合并时比较存活实体与对应 tombstone：

- tombstone 更新，则实体被隐藏。
- 存活实体更新，表示用户之后明确重新创建或恢复，实体可以再次出现。
- tombstone 在本版本中不自动清理，防止长期离线设备让旧数据复活。

## 纯合并函数

新增独立领域模块，负责：

1. 将旧版或新版状态规范化。
2. 为旧版记录生成稳定 ID、顺序和基线版本。
3. 分别按实体 ID 合并项目、打卡、随机条目、随机结果和阶段项目。
4. 对同 ID 选择最新版本。
5. 合并 tombstone 并过滤被更新删除的实体。
6. 按设置键执行最后修改优先。
7. 输出规范顺序，确保合并满足交换性和幂等性。

纯函数不访问 React、localStorage 或 Firebase。

## 旧数据升级

本地存储 envelope 升级为版本 2。读取版本 1 时：

- 保留所有项目、打卡、随机内容、每日随机结果、阶段项目和设置。
- 已有 ID 全部沿用。
- 打卡和每日随机结果使用稳定组合 ID。
- 缺失顺序按原数组位置生成。
- 有 `createdAt` 的实体可使用其时间作为基线；其他旧数据使用 `updatedAt: 0` 和空 `updatedBy`。
- 规范化过程必须确定性执行，不能每次加载生成不同 ID。

保存后使用版本 2；原始损坏数据仍沿用现有备份保护。

## 本地修改流程

所有编辑先同步完成两件事：

1. 更新可见 AppState。
2. 为受影响实体或设置写入新版本戳；删除则写 tombstone。

随后立即保存 localStorage。云端连接存在时，约 700ms 防抖后开始事务同步。网络离线或事务失败不回滚本地数据。

## Firestore 事务流程

每个同步码使用一个 Firestore 文档：

```
projectCheckinSyncSpaces/{syncCode}
  schemaVersion: 2
  data: AppStateWithSyncMeta
  updatedAt: serverTimestamp
```

连接和上传都使用 `runTransaction`：

1. 在事务中读取当前云文档。
2. 规范化本地和云端状态。
3. 调用同一个纯合并函数。
4. 仅当合并后的云内容发生变化时写回。
5. 事务完成后将相同合并结果保存到本地。

Firestore 自动重试事务冲突，避免两台设备同时上传时互相覆盖。

## 快照与渲染

`onSnapshot` 收到云端数据时先与当前本地状态合并。

- 若规范化同步内容没有变化，返回现有 React state 引用，不触发页面重渲染。
- 若有变化，只替换同步内容，保留本机视图、日期和交互状态。
- 若合并结果包含云端没有的本地内容，安排一次事务写回。
- 通过规范化比较避免快照、写回、再快照的无限循环。

## 状态显示

“云同步与数据”区域包含：

- 云同步码输入框。
- 新建同步码按钮。
- 连接同步按钮。
- 导入数据和导出数据按钮。
- 状态：仅本地、连接中、同步中、已同步、离线、同步失败。

页面首次加载时匿名登录。没有保存的项目同步码时保持“仅本地”；存在保存的项目同步码时自动重新连接。浏览器 `online` 事件触发待同步数据的事务合并。

## 导入导出

- 导出格式升级为版本 2，包含 AppState、所有实体版本、设置版本和 tombstone。
- 不导出匿名 Firebase UID、项目同步码或本机 deviceId。
- 导入版本 1 时自动升级。
- 导入版本 2 时保留同步元数据，随后与当前本地数据进行合集合并，而不是盲目覆盖。

## Firebase 配置与规则

应用使用 Firebase Authentication 匿名登录和 Cloud Firestore 模块化 SDK。项目仓库增加 `.firebaserc`、`firebase.json` 和 `firestore.rules`。

规则保留原集合并增加：

```text
match /projectCheckinSyncSpaces/{syncCode} {
  allow read, write: if request.auth != null
    && syncCode.size() >= 12
    && syncCode.size() <= 24;
}
```

规则部署前先验证编译，再部署到 `daily-calorie-tracker-3ec47`。

## 错误与离线处理

- 匿名登录或事务失败：保留本地数据，显示“同步失败”。
- `navigator.onLine === false` 或断网：显示“离线”。
- Firestore 快照非法：忽略非法快照，不替换有效本地状态。
- 恢复网络：自动运行事务，合并离线修改和云端修改。
- 切换同步码：关闭旧监听，再连接新文档。

## 自动测试

纯合并测试至少覆盖：

1. 两台设备独有数据取合集。
2. 同名但不同 ID 的数据分别保留。
3. 同 ID 最新修改生效。
4. 删除传播且旧设备数据不会复活。
5. 离线修改恢复后与云端数据取合集。
6. 重复合并结果保持一致，并验证交换合并结果一致。
7. 设置按字段最后修改优先。
8. 版本 1 自动升级且记录数量不变。
9. 导入导出保留同步元数据。

## 真实同步验收

使用两个隔离客户端：

- 客户端 A 通过 `127.0.0.1` 打开。
- 客户端 B 通过 `localhost` 打开。

两者拥有隔离的 localStorage 和匿名身份，但连接同一个项目同步码。验收流程：

1. A、B 各创建一个独有项目，双方最终都显示两个项目。
2. 创建同名不同 ID 项目，双方保留两个。
3. 同一项目冲突编辑后，最新修改在双方出现。
4. A 离线修改，B 在线修改，A 恢复后双方取合集。
5. 删除项目或打卡后，另一端同步删除；刷新旧端也不复活。
6. 快照无变化时不打断当前折叠状态和视图选择。

自动测试、生产构建、Firestore 规则和双客户端流程全部通过后，提交并部署 GitHub Pages，再在生产地址复验。
